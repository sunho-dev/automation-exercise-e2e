# Automation Exercise E2E 자동화

[![E2E Tests](https://github.com/sunho-dev/automation-exercise-e2e/actions/workflows/e2e.yml/badge.svg)](https://github.com/sunho-dev/automation-exercise-e2e/actions/workflows/e2e.yml)

쇼핑몰의 **회원가입 → 로그인 → 장바구니 → 주문·결제 → 탈퇴** 흐름을 직접 TC로 설계하고, Python + pytest + Playwright로 E2E 자동화한 프로젝트입니다.

![비로그인 주문 시나리오(ORD-002) 실행 화면](docs/images/ord-002.gif)

> 위 화면은 대표 시나리오 ORD-002입니다. 로그인 없이 상품을 담고, 결제 단계에서 회원가입한 뒤, 담아 둔 상품이 유지되는지 확인하고 주문과 탈퇴까지 진행합니다.

## 1. 왜 이 프로젝트인가

QA 자동화 실무에서 회원가입·로그인·주문(로그인/비로그인, 장바구니)·탈퇴 시나리오를 웹과 앱에서 자동화하고 매일 실행했습니다. 회사 코드와 데이터는 공개할 수 없어서, **같은 유형의 시나리오를 공개 사이트에 맞게 다시 설계하고 구현**했습니다. 실무 TC를 옮긴 것이 아니라 이 사이트의 화면과 동작을 직접 탐색해 새로 만든 TC입니다.

## 2. 왜 이 사이트인가

| 고려한 점 | 판단 |
|---|---|
| 테스트를 반복해서 돌려도 되는가 | 실제 운영 쇼핑몰은 자동 요청과 가짜 주문이 이용약관에 걸리고 서비스에 부담을 줍니다. Automation Exercise는 **자동화 연습용으로 공개된 사이트**라 반복 실행해도 문제가 없습니다. |
| 실무 시나리오를 재현할 수 있는가 | 처음에는 Sauce Demo를 검토했지만 **회원가입과 탈퇴가 없어서** 제외했습니다. 이 사이트는 가입, 로그인, 비로그인 장바구니, 결제, 탈퇴가 모두 있어 커머스 핵심 흐름을 처음부터 끝까지 이을 수 있습니다. 바로 주문 버튼은 없어서 그 시나리오만 제외했습니다. |
| 테스트 데이터를 깨끗하게 관리할 수 있는가 | 계정 생성·삭제 API가 공개되어 있어, **테스트마다 새 계정을 만들고 끝나면 지울 수 있습니다.** 테스트끼리 데이터가 섞이지 않습니다. |

사이트가 자체 TC 26개를 공개하고 있지만, 그대로 쓰면 다른 연습 프로젝트와 같아지기 때문에 **참고하지 않고 직접 설계**했습니다.

## 3. 테스트 설계

### 자동화 범위와 우선순위

| 기능 | TC | 우선순위 | 방식 |
|---|---|---|---|
| 회원가입 | SGN-001 정상 가입 / SGN-002 중복 이메일 | P1 | 자동 |
| 로그인 | LGN-001 정상 로그인 / LGN-002 틀린 비밀번호 | P1 | 자동 |
| | LGN-003 로그아웃 | P2 | 자동 |
| 장바구니 | CRT-001 담기 | P1 | 자동 |
| | CRT-002 수량 지정 담기 / CRT-003 삭제 | P2 | 자동 |
| 주문 | ORD-001 로그인 후 주문 / **ORD-002 비로그인 주문(결제 단계 가입)** / ORD-003 여러 상품·수량 주문 | P1 | 자동 |
| | ORD-004 배송지 = 가입 정보 확인 | P2 | 자동 |
| 탈퇴 | DEL-001 탈퇴 후 재로그인 실패 | P1 | 자동 |
| 수동 | SGN-003 / ORD-005 (필수값 누락), ORD-006 송장, DEL-002 재가입 | P2~P3 | 수동 |

**수동으로 남긴 이유**
- SGN-003, ORD-005: 빈 칸 입력은 브라우저 기본 검사가 막습니다. 사이트 기능보다 브라우저 동작을 확인하는 셈이라 자동화 효과가 작습니다.
- ORD-006, DEL-002: P3이라 자주 돌릴 필요가 적습니다.

→ 모든 TC를 자동화하기보다 **자주 깨지면 손해가 큰 흐름부터** 범위를 정했습니다.

### 검증 포인트 예시
- **ORD-002**: 가입 전에 담은 상품이 가입 후에도 장바구니에 남아 있는지 확인합니다. 커머스에서 놓치기 쉬운 지점입니다.
- **ORD-003**: 화면 금액을 숫자로 읽어 `상품별 합계 = 가격 × 수량`, `Total Amount = 합계의 합`을 계산으로 검증합니다.
- **DEL-001**: 탈퇴 완료 문구뿐 아니라, 같은 계정으로 **다시 로그인하면 실패하는지**까지 확인합니다.

## 4. 왜 이렇게 구조를 짰는가

```
pages/                        # 화면별 클래스: "어떻게 조작하나"
├─ home/home_page.py          #   상단 메뉴 (로그인·장바구니·로그아웃·탈퇴)
├─ login/login_page.py
├─ signup/signup_page.py
├─ products/products_page.py
├─ product_detail/...
├─ cart/cart_page.py
├─ checkout/checkout_page.py
├─ payment/payment_page.py
└─ account_result/...         #   가입·탈퇴 완료 화면
scenarios/                    # 기능별 시나리오: "결과가 어때야 하나"
├─ test_signup.py
├─ test_login.py
├─ test_cart.py
├─ test_order.py
└─ test_delete_account.py
conftest.py                   # 공통 준비·정리: 광고 차단, 테스트 계정 생성·탈퇴
docs/                         # TC 목록(CSV), 테스트 리포트, 실행 화면
```

| 결정 | 이유 |
|---|---|
| **Page Object Model (클래스)** | 화면 요소의 위치를 클래스 맨 위에 모아 둡니다. 사이트 화면이 바뀌면 그 화면 파일 한 곳만 고치면 됩니다. 실제로 P2 시나리오 3개를 추가할 때 새 화면 클래스 없이 `CartPage`에 함수 하나만 더해 끝났습니다. |
| **화면마다 폴더** | 화면 단위로 코드를 찾기 쉽고, 한 화면이 커지면 폴더 안에서 나눌 수 있습니다. |
| **page는 동작만, 검증은 시나리오에서** | `login()`에 "로그인 성공 확인"을 넣으면, 틀린 비밀번호 시나리오(LGN-002)에서는 함수 안에서 바로 실패해 에러 문구를 확인할 수 없습니다. 동작과 검증을 나누어 **같은 함수를 성공·실패 시나리오에서 재사용**하고, 시나리오 파일만 읽어도 무엇을 검증하는지 보이게 했습니다. |
| **시나리오 파일은 기능별, TC ID는 docstring에** | 파일 이름에 TC ID를 넣으면 ID가 바뀔 때 파일 이름까지 바꿔야 합니다. ID는 각 테스트 함수 설명에 적어 CSV와 연결했습니다. |
| **테스트 계정은 fixture로 준비·정리** | `test_account`는 API로 미리 가입시킨 계정이라 로그인·주문 테스트가 가입 화면 상태에 영향받지 않습니다. `new_account`는 가입 정보만 만들어, 가입 화면 자체를 검증하는 SGN-001·ORD-002에서 사용합니다. 둘 다 **테스트가 실패해도 끝나면 자동으로 탈퇴**시켜 계정이 쌓이지 않습니다. |
| **광고 요청 차단** | 광고가 버튼을 가리거나 로딩을 늦추면 테스트가 불안정해집니다. 모든 시나리오에 자동 적용했습니다. |

## 5. 문제 해결 기록

| 증상 | 원인 | 해결 |
|---|---|---|
| 상품을 담고 바로 장바구니로 가면 비어 있었습니다. | 담기는 백그라운드 요청인데, 끝나기 전에 페이지를 떠나 요청이 취소됐습니다. | "Added!" 팝업이 뜰 때까지 기다린 뒤 이동하도록 `add_to_cart()`에 넣었습니다. |
| 전체 실행 중 가끔 장바구니 삭제가 안 되거나 결제 팝업이 뜨지 않았습니다(간헐적 실패). | 버튼은 그려졌지만 페이지 스크립트가 연결되기 전에 클릭해서 클릭이 무시됐습니다. | 장바구니 화면에서 클릭하기 전에 페이지 로딩 완료를 기다리게 했습니다. 해당 시나리오를 5회 반복 실행해 15/15 통과를 확인했습니다. |
| Python 기본 `urllib`으로 계정 API를 호출하면 403이 났습니다. | 사이트가 기본 요청 형식을 차단했습니다. | Playwright의 요청 기능으로 호출해 해결했습니다. 덕분에 화면과 API를 한 도구로 다룹니다. |
| 완료 문구 비교가 실패했습니다(`Order Placed!` vs `ORDER PLACED!`). | 화면에서 CSS로 대문자로 바꿔 보여 줍니다. | 대소문자를 무시하고 비교했습니다. |

## 6. 실행 방법

```bash
python -m venv .venv
.venv\Scripts\activate            # macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
playwright install chromium

pytest -v                                         # 전체 실행
pytest -v --headed --slowmo 500 -k guest          # 브라우저를 띄워 ORD-002만 천천히 보기
pytest --html=docs/report.html --self-contained-html   # HTML 리포트 생성
```

## 7. CI (GitHub Actions)

[`.github/workflows/e2e.yml`](.github/workflows/e2e.yml)에서 전체 시나리오를 자동으로 실행합니다.

| 실행 시점 | 목적 |
|---|---|
| main 푸시, Pull Request | 코드 변경이 기존 시나리오를 깨뜨리지 않는지 합치기 전에 확인합니다. |
| 매일 오전 9시(KST) | 코드가 그대로여도 대상 사이트가 바뀌어 깨지는 시나리오를 잡습니다. 운영 모니터링에 가까운 역할입니다. |
| 수동 실행 | Actions 탭에서 필요할 때 실행합니다. |

실행이 끝나면 HTML 리포트를 결과물(Artifacts)로 남기고, 실패하면 스크린샷과 Playwright trace도 함께 남겨 다시 돌리지 않고도 원인을 볼 수 있게 했습니다.

## 8. 실무와의 관계

실무에서는 같은 유형의 시나리오를 **웹(Playwright)과 앱(Appium)에서 함께 실행해 결과를 교차 확인**했고, 매일 돌려 결과를 메신저로 공유했습니다.

실무에서도 처음에는 GitHub Actions로 정기 실행을 구성하려 했습니다. 그런데 앱 테스트는 실제 기기나 에뮬레이터가 필요해 클라우드 실행 환경에서 돌리기 어려웠고, 웹과 앱 결과를 함께 비교해야 했기 때문에 **기기가 연결된 PC에서 구글 시트 + 데몬 스케줄러로 운영**하는 방식으로 바꿨습니다. 이 사이트는 앱이 없어 **이 저장소에는 웹 E2E만** 있으므로, 원래 의도대로 GitHub Actions로 구성했습니다.
